# ADR-0038: Tonal ramps with checked annotations

## Status

Accepted. Additive — the resolved value of every existing token is unchanged,
verified. Covers the teal (brand) ramp only; the semantic families follow the
same recipe.

## Context

ADR-0018 defined a three-tier token architecture — primitive, semantic,
component — but only the semantic tier ever existed in CSS. `--ui-color-primary`
held a hex value directly, with `-hover` and `-active` holding two more, and the
dark theme holding three more again. Six literals, no stated relationship
between them, and nothing recording *why* `#004e58` is the hover of `#006470`.

The consequence is not aesthetic. Two things were impossible to answer from the
token file:

1. **Which shade of the brand colour is safe for text, on which canvas.** That
   knowledge lived in a person's head, or in a four-month-old report. Anyone
   picking a teal for a label was guessing.
2. **What the brand colour actually is.** `--ui-color-primary` is a role, and it
   holds a different hex in each theme. Neither is "the brand colour"; both are
   the role's value in a mode.

The Conciso design system answers both with a convention worth borrowing (the
structure, not the values): ramps of 50–900, one step marked as the brand
anchor, and the text-safe step marked with its measured ratio.

## Decision

**A tonal ramp as the primitive tier, with annotations the gate re-measures.**

`--ui-color-teal-{50…900}` is declared once on `:root`. The semantic tokens
alias into it — light theme takes 700/800/900 for primary/hover/active, dark
theme takes 300/200/100 — so a step is declared once and each mode picks a
different step of the same scale.

Steps 100–300 and 700–900 **are** the values that were already shipping, at the
step they belong to. The four gaps (50, 400, 500, 600) were generated by
perceptual interpolation in OKLab between them, which is why the ramp reads as
one scale rather than six literals plus filler. The contrast progression is
monotonic across the whole ramp, which is the cheapest evidence that the
interpolation is sound.

**Annotations are checked, not decorative.** A trailing comment may claim:

```css
--ui-color-teal-600: #0d7f89; /* T on surface(light) 4.76 */
--ui-color-teal-700: #006470; /* ★ · T on surface(light) 6.87 */
```

`check:contrast` (ADR-0037) now re-measures every one of them and fails if the
stated ratio is wrong, if a step marked `T` does not actually reach 4.5:1 on the
named canvas, or if a ramp family claims two `★` anchors. Seven annotated steps
are re-measured today.

This is the piece that makes the ramp worth having. A comment saying "safe for
text" is a comment; a comment the build re-measures is a contract. And it
answers both questions above from the token file alone: **700 is the anchor**,
**600 is the lightest text-safe step on light**, **500 is the lightest that
still carries text on dark**.

Naming: `--ui-color-teal-*` rather than a separate primitive prefix. A token
that names a hue rather than a role reads as a primitive on sight, and it keeps
one namespace — which matters because `check:contrast` and `check:css-tokens`
both parse `--ui-color-*` and would otherwise need to learn a second prefix.

Alternatives considered:

- **Generate the whole ramp from the anchor** and accept that the existing hex
  values shift to the computed steps. Rejected: it would change what every
  component renders, in the same change that introduces the mechanism. The
  additive constraint is what makes this reviewable — and the ramp is *more*
  honest for containing the values that actually shipped.
- **A separate primitive prefix** (`--ui-primitive-teal-700`, or Conciso's
  `--co-700`). Rejected: two namespaces for two gates to learn, in exchange for
  a distinction the hue-vs-role naming already carries.
- **Leave the annotations as prose in the manifest.** Rejected: that is where
  the previous text-safety knowledge lived, and it went stale. The manifest
  still carries the guidance; the ratio is now in the token file where the gate
  can reach it.
- **Ramps for every family in one change.** Rejected as scope: one family
  proves the recipe and the gate extension. Danger, success, warning, info and
  the neutrals follow, each additive in the same way.

## Consequences

- **The additive claim is verified, not asserted.** After re-pointing the four
  primary blocks at ramp steps, `check:contrast` reports the same 104 pairs
  passing with identical ratios — 6.87, 9.41 and 12.47 for primary, hover and
  active on white, exactly the computed ramp values. Nothing renders
  differently.
- **The annotation checker was negative-tested**, not read: a comment claiming
  5.00 where the colour measures 6.87 fails with both numbers named; a `T` mark
  on step 400 against the light canvas fails at 2.37; a second `★` in the teal
  family fails naming the step that already holds it.
- **124 tokens annotated** in the manifest (up from 114). Each ramp step's
  constraints say the thing that matters about a primitive: do not reference it
  from component CSS, use the semantic that aliases it.
- **The remaining families are now mechanical.** Same recipe: place the shipping
  values at their steps, interpolate the gaps in OKLab, mark the anchor and the
  text-safe steps, let the gate check them.
- **Open: nothing prevents a component from referencing a ramp step directly.**
  The manifest says not to; no gate enforces it. That is the same shape as the
  `--ui-font-display` hole ADR-0036 left, and the two should probably be closed
  by one gate that knows which tokens are primitives.
