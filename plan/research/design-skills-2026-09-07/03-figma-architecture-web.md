# Figma design-system architecture for 2025–2026: maintainable for designers, machine-readable for AI

Research date: 2026-09-07. Web-only research; see bibliography for every URL actually fetched. Claims not backed by a fetched page are marked **[not verified]**.

## 1. File & page structure

- Figma's own file-organization guide frames pages around a **workflow, not a taxonomy**: Cover → Visual research → Discovery → Flow → **Ready for development**, with the last "kept separate so nobody ships the wrong asset," plus optional User research / Prototype / Local components pages. ([Team, Folder, and File Organization](https://www.figma.com/best-practices/team-file-organization/))
- Figma explicitly recommends **spacer pages** — "a series of hyphens as the page name" — to visually divide sections in the page list, and says emoji/prefix conventions are a team preference, not a rule. ([Team, Folder, and File Organization](https://www.figma.com/best-practices/team-file-organization/))
- Defer structure decisions: "Leave it to the end of the process, once the direction is agreed" — impose page hierarchy after direction stabilizes, not while still exploring. ([Team, Folder, and File Organization](https://www.figma.com/best-practices/team-file-organization/))
- For **component libraries specifically**, Figma recommends **pages and frames as organizing containers** in addition to (not instead of) naming — this decouples the Assets-panel hierarchy from the component's actual name, so names "align with your codebase instead" of a forced slash path. ([Components, styles, and shared libraries](https://www.figma.com/best-practices/components-styles-and-shared-libraries/))
- On single file vs. multiple libraries: Figma's own analytics guide assumes a **multi-library reality** for teams past a certain size — e.g. splitting by platform "to ensure both platforms are being designed for equally," and running old/new design-system libraries side by side so usage can be tracked before deprecating the old one. Practitioner consensus (Medium, "2025 Master Guide") converges on the same "system of systems" pattern: one foundation/base library plus platform-specific libraries branching off it, traded off against the annoyance of designers enabling many libraries. **[search-derived, not independently fetched]** ([Design System Analytics](https://www.figma.com/best-practices/make-the-most-of-design-system-analytics/), [2025 Master Guide, Medium](https://medium.com/@claus.nisslmueller/structuring-and-splitting-large-scale-figma-design-systems-a-2025-master-guide-for-scalable-c1c3a7dabb0e))

## 2. Cover / overview / index pages

- Figma's minimum bar for a cover: "Covers make files discoverable. At minimum, include the file name and a short description," with extended covers adding screenshots, status, or team ownership. ([Team, Folder, and File Organization](https://www.figma.com/best-practices/team-file-organization/))
- Figma's own Design-Systems-103 post treats **documentation as a first-class deliverable with six required parts**: design principles, component library (usage, spec, code snippets, prototypes), visual style guide, technical implementation (APIs, a11y, framework guides), accessibility guidelines, and real usage examples. ([Documentation That Drives Adoption](https://www.figma.com/blog/design-systems-103-documentation-that-drives-adoption/))
- **Where documentation should live is genuinely split by team size**, per the same Figma post: large orgs (Google Material, IBM Carbon, eBay Evo) run dedicated external documentation sites; smaller teams start in Notion/Confluence, often hybridized with Storybook for the technical spec and Figma for the visual/usage guidance. ([Documentation That Drives Adoption](https://www.figma.com/blog/design-systems-103-documentation-that-drives-adoption/))
- Component-level description fields are the built-in "documentation inside Figma" mechanism: "designers have the option to add a text description to styles and components," which stays attached to every instance and surfaces to developers in the same place. ([Tips on Developer Handoff](https://www.figma.com/best-practices/tips-on-developer-handoff/))
- eBay's concrete anti-drift mechanism: "a custom linter to validate their documentation, which checks component usage against guidelines, verifies accessibility information is complete, ensures all images have alt text, and flags inconsistencies in naming or structure" — i.e., docs are gated by an automated check, not trust. ([Documentation That Drives Adoption](https://www.figma.com/blog/design-systems-103-documentation-that-drives-adoption/))

## 3. Component architecture

- Figma's official model for "base component" reuse: "Create reusable 'atom' components that you can nest in others to make updating easier" — a button with 16 permutations (state × size × platform) becomes one update point instead of 16. ([Components, styles, and shared libraries](https://www.figma.com/best-practices/components-styles-and-shared-libraries/))
- The `.base/` or `_base` prefix convention hides a private master from the published library ("adding a prefix such as a period (.) or an underscore (_)" stops it publishing) so designers can't drag the raw base onto a canvas — though the search results flag this as **partially broken**: prefixed components can still surface once nested inside another component in the same file. **[search-derived, not independently fetched]** ([Rootstrap: Figma base components](https://www.rootstrap.com/blog/how-to-start-with-figma-base-components))
- Figma's official component-property taxonomy has five types, each for a distinct job: **Boolean** (toggle a layer's visibility, e.g. an icon on a button), **Instance-swap** (substitute a nested component), **Text** (edit copy without deep-selecting), **Variant** (define a component-set axis — state/size/color), and **Slot** (2025 feature: a placeholder region where any layer can be dropped in without detaching). ([Explore component properties](https://help.figma.com/hc/en-us/articles/5579474826519-Explore-component-properties))
- Naming rule: "Component variants map to properties that align with your code components following the prop/value format used in popular frontend frameworks like React and Vue" — i.e., pick variant property names because they match the framework's prop names, not because they read naturally in the UI. ([Creating and Organizing Variants](https://www.figma.com/best-practices/creating-and-organizing-variants/))
- **Slots vs. variants** is the load-bearing 2025 decision. Figma's own framing: slots are for "components that appear frequently across screens" and "have accumulated excessive variants" — foundational containers like dialogs, menus, modals, cards, panels — where "structure stays consistent but content changes frequently." The explicit payoff for system owners: "Fewer variants, less maintenance, and stronger alignment to production," and slots eliminate the reason designers detach instances in the first place. Announced at Schema 2025 (Oct 2025); open beta as of March 5, 2026. ([Supercharge your design system with slots](https://www.figma.com/blog/supercharge-your-design-system-with-slots/), [Use slots to build flexible components](https://help.figma.com/hc/en-us/articles/38231200344599-Use-slots-to-build-flexible-components-in-Figma))
- Slot limitation to design around: "Component properties cannot be applied to layers from inside a slot" — you can insert an instance that already carries properties, but you cannot expose new properties on slot contents from the parent. ([Use slots to build flexible components](https://help.figma.com/hc/en-us/articles/38231200344599-Use-slots-to-build-flexible-components-in-Figma))
- Split rule of thumb (variants vs. separate components): "if two things would never appear in the same slot in a real screen, they should not live in the same set" — variants exist to swap states of the same object, not to bundle unrelated shapes. **[search-derived, not independently fetched]** Figma's own guide agrees from the code-fidelity angle, flagging that state-representing "hidden layers" inside one variant lose text overrides on swap and hurt discoverability versus separate, top-level variants. ([Components, styles, and shared libraries](https://www.figma.com/best-practices/components-styles-and-shared-libraries/))
- Icons: one component per icon, grouped by `icon/size/name` in the Assets tab, on a consistent grid (24×24 with a 20×20 live area is the most-cited convention, Material's included) so swapping via instance-swap never shifts alignment. **[search-derived, not independently fetched]** ([Icons in Figma — Best Practice, Medium](https://medium.com/@sbensidi/icons-in-figma-best-practice-0bdcc9b50954), [Name and organize components](https://help.figma.com/hc/en-us/articles/360038663994-Name-and-organize-components))
- Responsive width: use nested Auto Layout with min/max width on the parent, letting children resize between Fixed/Hug/Fill at each level — e.g. for a data table, "Min Width for the Row is the Width at that breakpoint, and Max Width for the Row is the Row Width of the next larger breakpoint." **[search-derived, not independently fetched]** ([Create a responsive card, Figma Help](https://help.figma.com/hc/en-us/articles/18894664907287-Create-a-responsive-card-with-auto-layout-and-constraints))

## 4. Tokens / variables

- Figma's canonical tiering: primitives are raw building blocks "that aren't directly applied in components or layouts"; semantic tokens carry meaning, e.g. `color-background-warning`; naming should favor role over appearance so a rebrand doesn't orphan the name. ([Design Systems 102](https://www.figma.com/blog/design-systems-102-how-to-build-your-design-system/))
- A **collection** is "a set of variables and modes," and Figma recommends splitting collections by tier/domain (primitives, semantic, component) and using in-collection **groups** to further segregate concerns (e.g., text vs. stroke colors). Variables can alias other variables ("apply a variable to another variable... also called 'aliasing'"), which is the mechanism that lets a semantic token point at a primitive and a component token point at a semantic one. ([Overview of variables, collections, and modes](https://help.figma.com/hc/en-us/articles/14506821864087-Overview-of-variables-collections-and-modes))
- Modes are the theming axis, and Figma frames them broadly: "Modes also represent the different contexts of our designs" — not just light/dark, but density, brand, device, or locale. ([Overview of variables, collections, and modes](https://help.figma.com/hc/en-us/articles/14506821864087-Overview-of-variables-collections-and-modes))
- Plan-tier limits reported in Figma's community forum (not confirmed on a pricing page in this research): Free = 1 mode/collection, Pro = 10, Organization = 20, Enterprise = 40; variables per collection capped at 5,000 across tiers. **[search-derived, not independently fetched]** ([Figma Forum: variable mode limits](https://forum.figma.com/suggest-a-feature-11/launched-all-plans-should-offer-more-than-4-variable-modes-13979))
- Export/interop: the W3C **DTCG** JSON spec is the emerging portability format across Tokens Studio, Style Dictionary, and Figma Variables; Tokens Studio's own docs describe choosing "W3C DTCG vs Legacy" token format and exporting to Figma as Variables and/or Styles keyed by name match. Community tooling (`figma-to-dtcg`, "Token Press") reads Figma's Variables via the Plugin API or REST API and emits DTCG JSON for Style Dictionary pipelines. **[search-derived, not independently fetched]** ([Token Format — Tokens Studio docs](https://docs.tokens.studio/manage-settings/token-format), [zeroheight: exporting design tokens from Figma](https://zeroheight.com/learn/exporting-design-tokens-from-figma-formats-tools-and-workflows/))
- Text/effect **styles** vs. variables is a real fork, not a redundancy: Figma's own phrasing is "Variables in Figma store single values such as colors, whereas styles hold more complex information" (e.g., a full type ramp or a multi-layer shadow) — use variables for atomic, mode-switchable values and styles for composite, rarely-switched ones. ([Design Systems 102](https://www.figma.com/blog/design-systems-102-how-to-build-your-design-system/))

## 5. Handoff & code mapping

- **Ready for dev** is a status, not a page: Figma's own file-organization guide keeps a dedicated "Ready for development" page/section specifically so "nobody ships the wrong asset" — signed-off work is physically separated from work in flux. ([Team, Folder, and File Organization](https://www.figma.com/best-practices/team-file-organization/))
- **Annotations** in Dev Mode are positioned as a curated post-design specification layer, not canvas clutter during iteration: "designers should go to Dev Mode to annotate" and share a link when done. Their real value over plain sticky notes is that they can reference live variables/components, so "developers can trust that the spec is aligned with the codebase," and measurement annotations "update" automatically as the design changes rather than going stale. ([The Art and Science of Annotations in Dev Mode](https://www.figma.com/blog/annotations-in-dev-mode/))
- **Code Connect** is the explicit bridge from a Figma component to its real production implementation: in Dev Mode it "will display true-to-production code snippets from your design system instead of autogenerated code examples," mapping real code props onto the Figma component's properties. Official/maintained targets: React, React Native, HTML (covering Web Components/Angular/Vue via HTML), SwiftUI, Jetpack Compose, Storybook, plus framework-agnostic config now positioned as the primary path; it requires Organization/Enterprise plan seats. ([figma/code-connect README](https://github.com/figma/code-connect))
- The **Dev Mode MCP server** hands an AI coding agent four kinds of context per node: component/variable/token metadata (with code syntax), multi-zoom screenshots, interactivity/pseudocode, and content (text/SVG/layer names/annotations). Figma's own stated rationale: generic LLMs "generate code matching their training data, not your specific codebase patterns," and every team's codebase is "a unique fingerprint that's difficult for LLMs to infer" — MCP context (plus Code Connect mappings) is what closes that gap. ([Introducing our Dev Mode MCP server](https://www.figma.com/blog/introducing-figma-mcp-server/))
- Storybook integration is explicitly **bidirectional, not a single source of truth**: the Storybook plugin "supports linking stories to Figma components, variants, and instances," and once linked, all instances of that Figma component carry the link — designers can preview the live Storybook story inside Figma, and developers can jump to the Figma source from Storybook. Figma's own help article stops short of naming one side as canonical. ([Storybook and Figma](https://help.figma.com/hc/en-us/articles/360045003494-Storybook-and-Figma))
- Layer/component naming is now explicitly an **AI-readability requirement**, not just tidiness: one practitioner account (found via search, not independently fetched) reports 62% of layers in an audited file were generic ("Frame 12," "Group 3"), and frames the stakes bluntly — unnamed layers are "annoying" to a human but "incomprehensible noise" to an AI agent reading the file through MCP, and can make an agent "misinterpret elements, leading to broken layouts or incorrect styling." **[search-derived, not independently fetched]** ([The Design System Is the Prompt, Medium](https://medium.com/@prateeksaini_71722/the-design-system-is-the-prompt-79bc3c341457))

## 6. Design review

- Figma's own analytics tooling is explicitly built to feed a review process, not replace it: flag components with unusually high **detachment rates** for investigation — while noting some components (e.g. a full-screen starter template) are meant to be detached, so the metric needs human judgment, not an automatic gate. Usage/adoption metrics (insertions per week, per team) are meant to justify **deprecation timing** for an old library once a new one's adoption is proven. ([Design System Analytics](https://www.figma.com/best-practices/make-the-most-of-design-system-analytics/))
- A practitioner "drift review" ritual (found via a design-tooling vendor's blog, fetched directly): weekly, put three things side by side — live product, Figma source, and code — and ask only "what changed on purpose?"; crucially, "a drift review ends with an owner, a deadline, and a decision," i.e., a checklist without an assigned owner is theater. ([Figma Design System Drift](https://figr.design/blog/figma-design-system-drift))
- A concrete a11y checklist for component review (found via search, not independently fetched): contrast tokens at ≥4.5:1 body text / ≥3:1 for a defined `focus/ring-color` token against both themes, full keyboard operability (Tab/Enter/Escape), visible focus rings (≥3px), ARIA labels/roles on interactive components, and a `spacing/touch-target` value of 44px minimum. **[search-derived, not independently fetched]** ([Accessibility in Design Systems](https://a11ypros.com/blog/accessibility-in-design-systems))
- Lint/audit plugins split into two camps: **style-consistency linters** (Roller, Design Lint, Yet Another Design Linter) that flag colors/type/effects/radii not bound to a shared style or variable, and newer **AI compliance auditors** (Design System Linter Pro, FigmaLint) that additionally score a11y and "developer readiness." **[search-derived, not independently fetched]** ([Best Figma plugins for design systems in 2026](https://story.to.design/blog/best-design-system-plugins-of-2026))
- A "definition of done" can live as a literal canvas widget: the Component To-Do List widget turns done-ness into an interactive checklist attached to the component frame itself, prompting reviewers on responsive breakpoints, accessibility compliance, and error-state coverage before a component is called finished. ([Component To-Do List](https://fountn.design/resource/component-to-do-list-design-system-checklist-for-figma/))

## 7. Anti-patterns

- **Detached instances**: figr.design's framing is that detachment is a symptom, not the disease — "a squad ships a feature under deadline... they detach an old instance, tweak the padding, and keep going," and those local edits harden into parallel, undocumented versions the next time someone copies them. Slots are Figma's structural fix, since they remove the reason to detach in the first place (see §3). ([Figma Design System Drift](https://figr.design/blog/figma-design-system-drift); [Supercharge your design system with slots](https://www.figma.com/blog/supercharge-your-design-system-with-slots/))
- **Hardcoded values**: same source, same mechanism — "a designer fixes a screen under deadline... they paste a hex value," engineering matches it with an equally hardcoded value in code, and the exception silently multiplies because nothing traces it back to a token. ([Figma Design System Drift](https://figr.design/blog/figma-design-system-drift))
- **Deep variant explosion**: Figma's own guidance names the failure mode directly — "Adding variants creates an unmanageable number of permutations, consider nesting instances or using base components instead," and calls out multi-brand theming as a common trigger. The 2025/2026 fix Figma is explicitly pushing is Slots, which target exactly this case. ([Creating and Organizing Variants](https://www.figma.com/best-practices/creating-and-organizing-variants/); [Supercharge your design system with slots](https://www.figma.com/blog/supercharge-your-design-system-with-slots/))
- **Unnamed/generic layers**: harmless to a human skimming the layer list, but actively breaks machine-readability — an AI agent reading the file via MCP has only the layer tree and names to reason from, so "Frame 12" / "Group 3" reads as noise it may misinterpret into wrong layout or styling. **[search-derived, not independently fetched]** ([The Design System Is the Prompt, Medium](https://medium.com/@prateeksaini_71722/the-design-system-is-the-prompt-79bc3c341457))
- **Documentation drift**: figr.design's diagnosis is that static docs decay by construction — "The file gets written during a cleanup sprint. Two releases later, the product has moved on and the doc is already lying" — and the only mechanisms shown to hold up are annotations/descriptions bound to live variables/components (so they can't say something the component doesn't), plus eBay-style automated linting of the documentation itself. ([Figma Design System Drift](https://figr.design/blog/figma-design-system-drift); [The Art and Science of Annotations in Dev Mode](https://www.figma.com/blog/annotations-in-dev-mode/); [Documentation That Drives Adoption](https://www.figma.com/blog/design-systems-103-documentation-that-drives-adoption/))

## Disagreements between sources

- **One file vs. many libraries.** Figma's practical materials (analytics guide, best-practices index) implicitly assume most serious teams already run multiple libraries and treat that as healthy scaling; several practitioner write-ups (Medium "2025 Master Guide," `figma.com/best-practices/team-file-organization`) instead frame a single well-organized file as sufficient until a specific pain point (permissions, load time, cross-team ownership) appears, and warn that too many libraries creates its own tax — designers "annoyed by having to enable/disable too many libraries." Neither side gives a hard threshold; the practical answer in both is "split when a concrete symptom appears, not on a schedule."
- **Where documentation belongs.** Figma's own Design-Systems-103 post is explicit that large orgs (Google, IBM, eBay) run **external** documentation sites, while Figma's Storybook-integration help article treats Figma and Storybook as **co-equal, bidirectional** sources with no canonical side. This is a real tension for a team deciding where "the" component doc lives: Figma-as-vendor's mature-org guidance points outward; Figma-as-product's own linking feature is built to avoid forcing that choice.
- **Base-component hiding via `.base`/`_base` prefixes.** Practitioner guides still teach the prefix convention as the way to keep a private master out of the published library, but the same search results flag it as unreliable in current Figma — hidden components can resurface once nested inside another component in the same file. This wasn't independently confirmed by fetching a page; flagged here as a live disagreement between "this is the pattern" and "this pattern is reportedly broken," not resolved by this research.
- **Slots vs. variants as _the_ 2025–2026 fix for variant explosion.** Figma's own blog and help center present Slots unambiguously as the answer. Independent practitioner commentary (e.g. a blog titled "Slots and the control paradox," found in search but not fetched) frames the same feature as a tradeoff — looser structure gains flexibility but weakens the guarantee that every instance of a component looks/behaves identically, which is a cost some systems can't accept. This research did not fetch that critique directly, so it is noted as a live tension rather than a settled claim.
