## PART A — figma-console-mcp (southleft)

### 1. Architecture

- **Two transports** [verified, github.com/southleft/figma-console-mcp README + architecture.md]:
  - **Desktop Bridge plugin (WebSocket)**: a Figma plugin (`~/.figma-console-mcp/plugin/manifest.json`) that the local MCP server talks to over WebSocket on ports **9223–9232** (auto-fallback if a port is taken; multiple simultaneous instances supported). This is the only path with real-time console-log capture, selection tracking, document-change watching, and full write access. Source: [README](https://github.com/southleft/figma-console-mcp/blob/main/README.md), [architecture.md](https://docs.figma-console-mcp.southleft.com/architecture.md).
  - **REST-API-only / Remote mode**: Cloudflare-Workers-hosted relay at `https://figma-console-mcp.southleft.com/{sse,mcp}`. Read-only via Figma's REST API alone (file structure, variables, styles, component images); gains **write** access only when paired with a running Desktop Bridge plugin through a Cloudflare Durable Object ("Cloud Write Relay", `PluginRelayDO`) using a single-use 6-character pairing code with a 5-minute TTL bound to the client's bearer token. [architecture.md]
- **Deployment models** [verified, README + setup.md]: `npx figma-console-mcp@latest` (local, full 114–121 tools depending on doc version — see discrepancy note below); local git clone + `npm run build:local`; Cloudflare-hosted cloud relay (101 tools, no real-time monitoring); self-hosted custom Cloudflare Worker.
- **Auth** [verified, README + setup.md]: Figma Personal Access Token (`FIGMA_ACCESS_TOKEN`, prefix `figd_`) for local/NPX mode. Required scopes: **File content (Read)**, **File versions (Read)**, **Variables (Read)**, **Comments (Read/write)**; docs explicitly say leave Webhooks, Dev resources, and Library analytics scopes at "No access." Remote/cloud mode instead uses OAuth 2.1 browser redirect (works on Figma Free/Pro/Org plans). Both transports run on non-Enterprise plans — the tool bypasses the REST Variables API's Enterprise gate by going through the Plugin API. [setup.md]
- **`ENABLE_MCP_APPS`** [verified, mcp-apps.md]: env flag, Local Mode only, requires an MCP client supporting the `ext-apps` protocol extension (`@modelcontextprotocol/ext-apps` SDK). When `false`/unset, "no app tools are registered, existing functionality is completely unaffected." Enables two interactive apps: **Token Browser** (searchable/filterable token table with color swatches, per-mode columns, click-to-copy) and **Design System Dashboard** (Lighthouse-style 0–100 score across six weighted categories: Naming & Semantics 25%, Token Architecture 20%, Component Metadata 20%, Accessibility 10%, Consistency 15%, Coverage 10%, with per-finding remediation). Feature is marked experimental. A non-interactive fallback, `figma_audit_design_system_report`, reproduces the same scoring as plain JSON without needing the flag. [README, mcp-apps.md]

### 2. Documented end-to-end workflows

- **Design system extraction pipeline** (Local Mode only — writes to the filesystem) [verified, CHANGELOG v1.40.0 + README]: `figma_ds_analyze` (scans a production codebase; detects framework/styling/vendor layers, e.g. shadcn/Radix/MUI/Chakra; classifies components vendored/wrapped/pure-vendor/bespoke; flags missing primitives) → `figma_ds_extract_tokens` (mines CSS custom properties, SCSS vars, Tailwind config, shadcn HSL triples, utility-class frequency into DTCG tokens with provenance in `$extensions`) → `figma_ds_scaffold` (generates a design-system package skeleton: `package.json`, token files, typography/iconography showcase docs) → `figma_ds_setup_storybook` (wires Storybook to the source app's theme layers, fonts, custom utilities, `@layer` defs, adds a theme toolbar) → `figma_ds_extract_component` (per-component manifest: source, prop contracts, observed variants, style touchpoints, CSF3 story scaffolds) → `figma_ds_verify` (deterministic fidelity checks: DTCG validity, alias integrity, CSS-expression quoting, Storybook `var()` resolution, story/porting coverage, Figma round-trip readiness) → `figma_ds_status` (persists porting progress across sessions). Round-trip closes via `figma_import_tokens` back into Figma variables. Large extraction reports are compressed to `<outDir>/.extraction/analysis.json` to avoid context overflow. This 7-tool pipeline is new in **v1.40.0** and is the most complete "workflow" the maintainers document; the hosted docs site's `use-cases.md` page references it but (per WebFetch) does not give the same tool-by-tool detail as the CHANGELOG — I treat the CHANGELOG as the more authoritative source here. [CHANGELOG.md, README.md]
- **Design-to-code workflow** [verified, README + use-cases.md]: `figma_get_component_for_development` (spec + high-res image) → (write code) → `figma_check_design_parity` (diffs Figma spec vs. code implementation, returns a fix-item report) → optionally `figma_generate_component_doc` (merges design data with git log + Figma version-history diffs into a markdown doc with atomic-design level, a11y notes, implementation details). No explicit prerequisites beyond having a component to extract; the use-cases page shows this pattern conceptually but the README has the concrete tool order.
- **Lint / audit workflows** [verified, README]: `figma_lint_design` (14 WCAG checks, conformance-tagged, scoped to multi-line text where relevant) and `figma_scan_code_accessibility` (axe-core scan of code, with a text-spacing-support advisory) run independently; `figma_audit_design_system_report` is the data-only twin of the MCP-Apps Dashboard (5-minute cache, six-category scoring, works in any MCP client without `ENABLE_MCP_APPS`). `figma_audit_component_accessibility` exists as a per-component scorecard tool (named in the tool inventory and in the companion skills repo) but its exact I/O wasn't detailed in any fetched page. [unverified: exact params of figma_audit_component_accessibility]
- **Token workflows** [verified, README + CHANGELOG v1.34.0]: Export — `figma_export_tokens`, 10 formats (DTCG legacy/2025.10, CSS, Tailwind v3/v4, SCSS, TS module, JSON flat/nested, Style Dictionary v3, Tokens Studio), with `scopes`/`codeSyntax` round-tripped via `$extensions`. Import — `figma_import_tokens` performs a **full diff-and-apply**: creates missing collections/variables, applies renames via round-trip ID tracking, writes real `VARIABLE_ALIAS` references (not comments), deletes only under `strategy: "replace"`; accepts both DTCG dialects. Bootstrap — `figma_setup_design_tokens` creates a collection + modes + variables in one call, resolving DTCG brace references to real aliases. The Token Browser MCP App gives an interactive read-only view of the same data.
- **Version history / changelog workflows** [verified, README + CHANGELOG]: `figma_list_versions` → `figma_get_version_snapshot` (reconstructs file state at a past version) → `figma_diff_versions` (component/binding deltas, with scope-coverage warnings so it doesn't silently miss out-of-scope nodes) → `figma_generate_version_changelog` (markdown with per-finding attribution) → `figma_blame_property` / `figma_blame_variant` (binary-search blame walkers). Works in all transport modes for read, but git-sourced history (used by `figma_generate_component_doc`'s optional `history.git` parameter, added v1.38.0) is Local-Mode-only and "degrades gracefully" on missing scopes, pruned versions, or untracked paths.
- **Annotations & dev status** [verified, tools.md via WebFetch]: `figma_get_annotations` (reads annotations, optional `traverseChildren`) / `figma_set_annotations` (writes/clears categorized annotations, plain text or markdown, with `pinned` properties) / `figma_get_annotation_categories` (lists categories for the current file). No standalone "dev status" tool was found in any fetched page — only annotations and the general dev-inspection tools (`figma_get_component_for_development`) surfaced. [unverified: a distinct "dev status" tool may not exist; treat as not found rather than confirmed absent]
- **Slots** [verified, tools.md + README, all require Desktop Bridge]: `figma_create_slot` → `figma_get_slots` → `figma_append_to_slot` (clone-mode: copy an existing node in; create-mode: spawn a new typed node) → `figma_reset_slot` (clear) → `figma_add_slot_property` (bind a component property with `preferredValues`). Supports standalone components and variants inside component sets; docs note beta restrictions "lifted at GA," implying slots shipped as beta before general availability.

### 3. Claude Code skills / prompt library shipped by the maintainers

Yes — but as a **separate companion repository**, not inside the main server: **[southleft/figma-console-mcp-skills](https://github.com/southleft/figma-console-mcp-skills)** [verified]. It repackages the MCP's most powerful capabilities as 22 Markdown skills for use with the **native Figma MCP server** (not figma-console-mcp itself), organized into five functional areas: (1) Tokens & Variables (4 skills — export to DTCG/CSS/Tailwind/SCSS/TS/JSON, non-destructive import, bootstrap/manage), (2) Components & Design Systems (5 skills — variant state-machine + visual-diff analysis, grid organization, unified DS inventory extraction, deep hierarchy navigation), (3) Quality & Accessibility (4 — WCAG 2.2 lint + DS audit, per-component a11y scorecards, axe-core code scanning, design-to-code parity), (4) Versioning & Collaboration (4 — version snapshots/diff, changelog gen, binary-search blame, comment read/write with node pinning), (5) Documentation/Annotations/FigJam/Slides (4). Each skill folder has `SKILL.md` (name/description frontmatter) + `scripts/*.js` (for the `use_figma` tool, plain JS with top-level `await`) + `scripts/*.mjs`/`*.sh` (REST API/code-side ops) + local `references/`. 18 of 22 skills need no token (OAuth via Figma's connector); only the 4 REST-API skills (version history, changelog, blame, comments) need an explicit `FIGMA_TOKEN` because the Plugin API can't reach those endpoints. Install via `npx skills add southleft/figma-console-mcp-skills`, zip upload to claude.ai, or git clone for Claude Code/Cursor. Deliberately does **not** duplicate the native Figma MCP's own tools (`get_design_context`, `get_screenshot`, `get_metadata`, `get_variable_defs`, `search_design_system`, Code Connect, file creation). No `.claude/` directory or AGENTS.md-style guidance was found inside the main `figma-console-mcp` repo itself. [verified via WebFetch of the skills repo README; unverified: I did not open individual SKILL.md files inside it]

### 4. Limitations, rate limits, payload caps, version

- **Remote SSE**: 9 tools, strictly read-only. **Cloud Mode**: 101 tools but no real-time monitoring (console logs, selection tracking, doc-change watching) since there's no persistent local process. [README]
- **Payload/size caps** [verified, tools.md + README]: `figma_get_library_component_by_key` auto-compresses/strips responses over **500KB**; `figma_execute` default timeout **5000ms**, configurable up to **30000ms**; `figma_batch_create_variables`/`figma_batch_update_variables` cap at **100 variables/batch**; `figma_create_component_set` hard-caps at **100 variants** with auto-scaling timeout (~1.2s/variant, 30s floor/2min ceiling, warns above ~40 variants); `figjam_create_stickies` caps at **200 stickies/batch**; `figma_watch_console` max duration **300 seconds**; `figma_get_console_logs` defaults to **100 logs** (configurable via `count`). No global API rate limit is documented anywhere in the fetched material — the maintainers don't appear to publish one, likely because they sit on top of Figma's own (undocumented-here) REST/Plugin-API limits.
- **Screenshot/cache staleness** [verified, architecture.md]: screenshots are disk-based with a **1-hour TTL cleanup**; `figma_get_component_image` URLs expire after **30 days**; console logs use an in-memory circular buffer (default 1000 entries) cleared on server restart. No stale-cache behavior is documented for component/variable data beyond standard REST caching.
- **Component descriptions**: Desktop Bridge reads reliably; the plain REST API is called out as "historically unreliable" for this field — this is in fact the tool's own reason for existing (README opens with "bypass...the REST API's component description bug").
- **Version and date**: **v1.40.0**, dated **2026-08-16** [verified, CHANGELOG.md and README cross-agree]. npm search separately surfaced a **1.38.0** listing timestamp lag typical of registry mirrors (jsdelivr/unpkg showed 1.38.0) — the CHANGELOG.md is the more current source of truth. Tool count is reported inconsistently across pages: README says "114 Local / 101 Cloud / 9 Remote," setup.md says "121 tools" for local — likely a documentation drift between pages rather than two different real counts; flagging as **[unverified: exact current local tool count, 114 vs 121]**.

## PART B — Anthropic guidance on authoring Agent Skills

### 1. SKILL.md format, naming/description, progressive disclosure, size

- **Required frontmatter** [verified, platform.claude.com/.../overview + best-practices]: only `name` and `description`. `name`: ≤64 chars, lowercase letters/numbers/hyphens only, no XML tags, cannot contain "anthropic" or "claude". `description`: non-empty, ≤1024 chars, no XML tags, **must state both what the skill does and when to use it**, and must be written in **third person** ("Processes Excel files...", never "I can help..."/"You can use this..."). No `allowed-tools` field appears in the *general* SKILL.md spec pages I fetched — the frontmatter Claude Code itself documents is minimal (name/description); a `license` field appears optionally in Anthropic's own example skills (e.g. `frontend-design/SKILL.md` has `license: Complete terms in LICENSE.txt`), and skill-creator's guide separately mentions an optional `compatibility` field for required tools/dependencies. [verified for skill-creator; the platform docs' canonical two-field list is the one to trust for "required" fields]
- **Naming**: prefer **gerund form** (`processing-pdfs`, `analyzing-spreadsheets`) or noun-phrase/action-oriented alternatives; avoid vague (`helper`, `utils`), overly generic (`documents`, `data`), or reserved-word names.
- **Progressive disclosure — 3 levels** [verified, overview + best-practices]:
  1. **Metadata** (name+description) — always loaded, ~100 tokens/skill.
  2. **SKILL.md body** — loaded only when the skill triggers, target **under 5k tokens** per the overview's cost table and **under 500 lines** per the best-practices checklist (both pages state this as the ceiling before you must split content out).
  3. **Bundled resources** (`references/*.md`, `scripts/*.py|js|sh`, `assets/*`) — loaded/executed only as referenced; **no context cost** until accessed. Scripts run via bash and only their *output* enters context, not their source.
- **When to use scripts vs. prose**: prose/text instructions ("high freedom") for tasks where "multiple approaches are valid... decisions depend on context"; medium freedom = parameterized pseudocode/templates; **scripts ("low freedom")** for fragile, error-prone, must-be-consistent, must-follow-exact-sequence operations (their example: database migrations). Guidance explicitly frames this as a "narrow bridge vs. open field" analogy. Scripts should "solve, don't defer" — handle errors internally rather than surfacing raw exceptions for Claude to improvise around, and avoid unexplained "voodoo constants."
- **Structural rules that matter in practice**: keep references **one level deep** from SKILL.md (don't chain SKILL.md → advanced.md → details.md — Claude may only partially read nested files via `head`); give reference files >100 lines a table of contents; avoid time-sensitive statements (use a collapsible "old patterns" section instead of "before/after [date]" language); use consistent terminology throughout (pick one term per concept, e.g. always "API endpoint," never mixing in "URL"/"route").

### 2. Patterns for skills wrapping MCP servers

- **Fully-qualified tool names** [verified, best-practices, "MCP tool references" section]: always reference MCP tools as `ServerName:tool_name` (e.g. `BigQuery:bigquery_schema`, `GitHub:create_issue`) — omitting the server prefix risks "tool not found" errors when multiple MCP servers are loaded simultaneously. This is the single most directly relevant rule for a skill that wraps figma-console-mcp: reference its tools as e.g. `figma-console:figma_check_design_parity`, not bare `figma_check_design_parity`.
- **Keeping tool lists from going stale**: no dedicated mechanism is documented (no auto-sync feature). The closest documented practice is generic: don't hardcode assumptions Claude can verify itself, and structure content so unused tool docs cost nothing until read (progressive disclosure absorbs some staleness risk by deferring detail to reference files you can update independently of SKILL.md's core flow). The **figma-console-mcp-skills** companion repo's own solution is organizational, not automated: it deliberately keeps a narrow non-overlapping tool surface per skill (see Part A §3) so each skill's tool list stays small and easy to hand-audit.
- **Encoding multi-step workflows** [verified, best-practices "Workflows and feedback loops"]: for complex tasks, provide a **literal copy-pasteable checklist** ("Copy this checklist and track your progress: `- [ ] Step 1...`") that Claude checks off as it proceeds; number the steps; state **stop conditions** explicitly ("Only proceed when validation passes," "If validation fails: fix issues, run validation again"). The "plan-validate-execute" pattern is recommended for batch/destructive/high-stakes operations: analyze → **write a structured plan file** → **validate the plan with a script** → execute → verify — this closes exactly the kind of gap a Figma-write workflow (e.g. bulk `figma_batch_update_variables`) would need.
- **Verification steps**: "implement feedback loops" — run validator → fix errors → repeat; make validation scripts verbose with actionable errors (their example: "Field 'signature_date' not found. Available fields: ..."); explicitly state "if X fails, return to step Y."

### 3. Evaluating and versioning a skill

- **Evaluation is the documented starting point, not an afterthought** [verified, best-practices "Build evaluations first"]: create evals **before** writing extensive docs. Process: (1) run Claude on representative tasks *without* the skill, document gaps; (2) build ≥3 test scenarios targeting those gaps; (3) establish a no-skill baseline; (4) write minimal instructions to pass the evals; (5) iterate. An eval is a JSON record of `{skills, query, files, expected_behavior}` — Anthropic states plainly there is **no built-in runner**; you write your own harness.
- **skill-creator** (in `anthropics/skills`) is the maintained, more mechanical version of this loop [verified, github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md]: draft/interview → write SKILL.md → generate `evals.json` test prompts + assertions → spawn all runs → grade (writes `grading.json`/`metrics.json`/`timing.json` per eval) → aggregate into `benchmark.json`/`benchmark.md` → launch an HTML `eval-viewer` → read qualitative feedback → iterate, tracked per `iteration-N/` folder; supports a "blind comparison" mode between two SKILL.md drafts. A separate **"Description Optimization"** loop specifically targets trigger accuracy: generate trigger-eval queries → run the *current* description 3× per query to get a reliable trigger rate on a 60/40 train/held-out split → have Claude propose description rewrites from the failures → re-score on both splits → repeat up to 5 iterations → apply the winner. Its own guidance leans toward writing **"pushy" descriptions** to counter under-triggering (example given: spell out synonyms/adjacent phrasings the user might say, e.g. "...whenever the user mentions dashboards, data visualization, internal metrics... even if they don't explicitly ask for a 'dashboard'").
- **Versioning/changelog**: no version field or CHANGELOG convention is mandated anywhere in the fetched Anthropic material. skill-creator's explicit instruction when updating an *installed* skill is to **keep the original directory name and `name:` field unchanged** (never emit a `-v2` folder), edit a copy in `/tmp/`, and repackage under the same name — i.e. skills version by overwrite-in-place, not by parallel version identifiers. [verified — this is a documented anti-pattern warning, not merely an absence of guidance]
- Testing should cover **all target model sizes** (Haiku/Sonnet/Opus) since a skill written for Opus's inference "might need more detail for Haiku."

### 4. Official design-related example skills

From `anthropics/skills` (19 skill folders total, confirmed by directory listing) [verified, github.com/anthropics/skills/tree/main/skills], the design-adjacent ones are: **frontend-design**, **canvas-design**, **brand-guidelines**, **theme-factory**, **web-artifacts-builder**, **algorithmic-art**, **doc-coauthoring**. (No skill literally named "hifi-design" was found in this repo as of fetch time — that name may exist elsewhere or under a different label. [unverified: hifi-design not found])
- **frontend-design** [verified structure, github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md]: ~71 lines total, **no `references/`/`scripts/`/`assets/` subfolders — entirely single-file prose** (headings: Frontend Design → Ground your designs in the subject matter → Design principles → Process: plan/review-against-brief/build/critique → Restraint and self-critique → More on writing in design). This is a "high freedom" skill by the best-practices taxonomy: it gives aesthetic-direction heuristics (brutalist, maximalist, retro-futuristic, luxury, organic, etc.) rather than scripts, deliberately leaving implementation (HTML/CSS/JS, React, Vue) to judgment.
- **canvas-design**: visual-art generation (.png/.pdf) using named design philosophies — per search-result summaries only; SKILL.md internals not separately fetched. [unverified: internal structure]
- **brand-guidelines**: applies Anthropic's own brand tokens (colors Dark #141413/Light #faf9f5, accents Orange #d97757/Blue #6a9bcc/Green #788c5d; fonts Poppins headings/Lora body) to artifacts — a good structural precedent for a "hardcode the token values directly in SKILL.md, no bundled files" design-system skill.
