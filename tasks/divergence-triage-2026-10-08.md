## Per-item evidence

### 1. Pagination `page`

- Angular: `readonly page = model(1)` at `libs/angular/src/lib/pagination/atl-pagination.ts:111`; `goTo` calls `this.page.set(clamped)` (`:147`). Works with `[(page)]` or `[page]` plus `(pageChange)`, and works unbound.
- React: `page = 1` prop, `onPageChange?.(clamped)` only; no state (`libs/react/src/lib/pagination/atl-pagination.tsx:75-83`, handler around `:91`).
- Vue: `page` prop, `emit('pageChange', clamped)` (`libs/vue/src/lib/pagination/atl-pagination.vue:19-60`); JSDoc states "Controlled".
- Verified (probe): React and Vue with `page=2` and no handler, click Next: `aria-current` stays on 2; the handler or emit receives 3. So the two are strictly controlled; Angular is not.
- Record: `allowlists.js:986` lists only `AtlPaginationSpec:onPageChange:react` (event naming). The contract `pagination.contract.ts` is empty. Vue JSDoc documents it; React and Angular do not mention it.
- Intended: spec `AtlPaginationSpec` has `page?: number` only. Mapping `model()` to controlled prop plus change event is the same rule `check:props` already applies to `on<X>Change`. Figma master: `page` is "code-only", illustrative axis.
- Class b. Fix: JSDoc on React noting "controlled, you must update `page`". Contract entries do not fit (not a Figma difference). Optional (M, additive): internal state when `page` is undefined, the way `AtlStepper` React already does (`isControlled` at `atl-stepper.tsx:72`). Not breaking.

### 2. Tooltip `atlTooltipPosition` flip

- Angular: two-entry position arrays (preferred then opposite) in `libs/angular/src/lib/tooltip/atl-tooltip.ts:51-116`, `withPush(true)` at `:216`. JSDoc `:144` "Falls back to the opposite side if clipped". The position is read once when the overlay is created (`createOverlay`, `:211`), so changing `atlTooltipPosition` later does not apply to an existing overlay (minor).
- React: no flip, only the CSS class `position-${atlTooltipPosition}` (`libs/react/src/lib/tooltip/atl-tooltip.tsx:120`). The JSDoc at `:15` repeats "Falls back to the opposite side if clipped": false.
- Vue: same CSS class (`atl-tooltip.vue:90`); JSDoc says "Preferred tooltip placement".
- Record: `allowlists.js:70-77` `VARIANT_AXIS_EXCEPTIONS` records only that Angular uses no `.position-*` class (CDK overlay vs CSS). `atl-tooltip.native.css` header cites ADR-0148 for the wrapper structure. Nothing records "no flip in React/Vue". Tooltip contract has no note.
- Found on the way, verified: Vue sets no `aria-describedby` on the trigger and the tooltip has no id (probe: `aria-describedby = null`, `id = (none)`). Angular sets it (`atl-tooltip.ts:137`), React sets it while visible (`atl-tooltip.tsx:80-87`, probe confirmed). The tooltip metadata claims "Uses aria-describedby". `check:a11y-parity` is green because `a11y-tree.ts` does not record `aria-describedby` (snapshots only hold role and name). That is a gate blind spot.
- Intended: Figma master "tooltip role, anchored via aria-describedby on the trigger"; position axis above|below|left|right. Flip is not in the spec or master.
- Class: React JSDoc is wrong (c, doc), no-flip is b, Vue missing `aria-describedby` is c (a11y).
- Fix: S for JSDoc plus Vue `aria-describedby` (id on tooltip, set on the slotted first element like React). A real flip in React/Vue is L (needs measuring or Popover/anchor positioning); only do it if wanted. Not breaking.

### 3. Stepper `linear`

- Angular `isReachable`: `steps.slice(0, index).every((s) => s.completed || s.optional)` (`libs/angular/src/lib/stepper/atl-stepper.ts:147-154`). React: identical (`libs/react/src/lib/stepper/atl-stepper.tsx:113-119`). Vue: identical (`libs/vue/src/lib/stepper/atl-stepper.vue:89-95`).
- Verified (Vue and React probes): `linear`, A completed, B optional, C pending: C's header button is enabled. Angular verified by reading only.
- So the premise "Vue only" is out of date: the logic is the same in all three. What differs is wording. Angular JSDoc `:108-111`: "only navigate to completed steps or the next pending step" (omits optional). React JSDoc `:59`: "until previous steps are completed". Vue JSDoc `:43` is the accurate one. The Figma master line says "only the active and completed steps are clickable".
- Class b (docs). Fix S: align the three JSDoc lines with Vue's, correct the Figma master description (Figma edit needs the Desktop Bridge). Not breaking. Existing specs do not pin the optional-skipping rule for any framework (they only test the "Optional" label); add one `play` or spec per framework (S).

### 4. `errors` type

- Angular: `input<readonly WithOptionalFieldTree<ValidationError>[]>([])`, rendered as `error.message`, tracked by `error.kind` (e.g. `libs/angular/src/lib/input/atl-input.ts:140`). The type comes from Signal Forms and is bound by `[formField]`.
- React and Vue: `errors?: string[]` on all seven form controls (e.g. `libs/react/src/lib/input/atl-input.tsx:52`, `libs/vue/src/lib/input/atl-input.vue:19`).
- Record: `allowlists.js:853-876` (21 `kind: 'gap'` entries): "a shared type is a contract change with its own ADR... Unresolved". `tasks/todo.md:2092` repeats it. No ADR.
- Intended: undecided. The spec has no `errors`.
- Options for the owner: (1) spec type `AtlFormError = { kind: string; message: string }`; Angular keeps accepting `ValidationError`, which is structurally compatible, and React/Vue accept `string | AtlFormError`. Additive everywhere, no break. (2) Keep `string[]` as the spec type and make Angular map it internally from `ValidationError` (hides `kind`; Angular users bind `[formField]` and lose nothing visible). (3) Leave it as a recorded `design` difference (Angular is the workshop framework and the only one with a forms integration). Recommendation: (1).
- Also noted, not part of the question: React radio-group renders its errors with `role="alert"` plus `aria-live` (`atl-radio-group.tsx:188`), the others use `aria-live="polite"` only.
- Effort M, breaking only if the Angular type is narrowed.

### 5. Breadcrumbs "current"

- Angular: no `current` input; `isCurrent = myIndex === lastItemId` via the `ATL_BREADCRUMBS` token (`libs/angular/src/lib/breadcrumbs/atl-breadcrumbs.ts:137-139`). "Last" is the last registered item, not necessarily the last in the DOM when items change dynamically.
- React: `AtlBreadcrumbs` does `cloneElement(child, { current: true })` on the last direct child (`libs/react/src/lib/breadcrumbs/atl-breadcrumbs.tsx:40-47`). The item still has a `current` prop. Verified: `<AtlBreadcrumbItem current={false}>` as last child is still current. Verified: items wrapped in a `Fragment` get no current item at all.
- Vue: no auto-marking; `AtlBreadcrumbItem` has `current` prop (`atl-breadcrumb-item.vue:6-15`), every story passes `:current="true"` by hand. Verified: no `aria-current` without it.
- Record: `allowlists.js:894-902` records `AtlBreadcrumbItemSpec:current:angular` as `kind: 'gap'`: "real API decision, not this gate". Note its claim "React and Vue model `current` as a settable prop" is only half true for React. The `breadcrumb-item.contract.ts` has only `href`. The Figma BreadcrumbItem master has an axis `current: false | true` (not a Boolean, because it recolours and removes the separator). The breadcrumbs metadata says "The item with `current` carries aria-current".
- Intended: the spec and the master both model `current` as explicit item state; the docs for Angular and React say "last item is automatic".
- Class d. Options: A) auto-detect everywhere, keep `current` as an optional override (`current ?? isLast`): Angular adds an optional input, React stops forcing it, Vue auto-detects via provide/inject. Most consistent with the Figma axis, additive for Angular and React, a behaviour change for Vue (items that omitted `current` become current when last, which is almost always what the author wants). B) explicit everywhere: Angular and React lose auto-detection (breaking, and worse ergonomics). C) record the difference as settled. Recommendation: A.
- Effort M.

### 6. Keyboard behaviour vs `accessibility.keyboard`

**6a Menu.** Metadata lists open on Enter/Space/ArrowDown with focus on the first item, Arrow Up/Down wrap, Home/End, Tab closes, Escape returns focus, submenus.

- Angular: `@angular/cdk/menu` (`libs/angular/src/lib/menu/atl-menu.ts:40`), so APG behaviour comes from the CDK (inferred from the CDK; Angular not run).
- React: only Escape and outside mousedown, document-level (`libs/react/src/lib/menu/atl-menu.tsx:156-175`). Vue: same (`atl-menu-trigger.vue:47-71`). Items are native `<button role="menuitem">`.
- Verified by probe in both: Enter opens the menu but focus stays on the trigger; ArrowDown and End do nothing; Escape closes (focus is on the trigger only because it never left); in React, Tab leaves the menu open.
- Record: none. A11y parity does not compare keyboard. Menu has `role="menu"` without the keys that role promises (APG: menu role implies Arrow navigation), so this is more than a metadata mismatch: screen-reader users in browse or focus mode expect it.
- Class c in React and Vue. Fix L: roving focus (focus first item on open, Arrow/Home/End with wrap, skip disabled, Tab closes, Escape returns focus), plus a spec per framework. Submenus are not implemented in React or Vue; either implement or reword the metadata with a "(Angular only)" note (b). Not breaking.

**6b Tabs.** Metadata: Arrow Left/Right select and focus, wrap, Home/End, skip disabled.

- Angular `onTabKeydown` selects and calls `.focus()` (`libs/angular/src/lib/tabs/atl-tabs.ts:111-140`). React does `setIndex` plus `.focus()` (`libs/react/src/lib/tabs/atl-tabs.tsx:97-121`).
- Vue `onKeydown` only calls `selectTab` (`libs/vue/src/lib/tabs/atl-tab-group.vue:80-110`); no focus call. Verified: after ArrowRight, T2 is `aria-selected` but `document.activeElement` is still T1, whose tabindex is now -1.
- A stale comment in `vue/src/lib/tabs/atl-tabs.spec.ts:28-29` says React/Angular use manual activation; the code shows they do not, so the comment is wrong.
- Class c (Vue). Fix S: focus the target button after select. Not breaking. Minor: Angular marks disabled tabs with `aria-disabled` while React/Vue use native `disabled`.

**6c Select.** React and Vue render a native `<select>` (`react/src/lib/select/atl-select.tsx:95`, `vue/.../atl-select.vue:85`). Angular is a CDK listbox with a key manager and type-ahead (`angular/.../atl-select.ts:331-412`). Recorded as `design` in `A11Y_PARITY_EXEMPT` (`allowlists.js:399-405`, ADR-0007), but the metadata keyboard text (written from Angular) describes a custom listbox. Class a for the structure, b for the metadata, which should say native browser behaviour applies in React and Vue. Fix S (metadata note). Not breaking.

**6d Combobox.** Metadata: Arrow moves between enabled filtered options. Angular filters disabled indices (`atl-combobox.ts:305-315`). React `handleKeydown` (`libs/react/src/lib/combobox/atl-combobox.tsx:151-170`) and Vue `onKeydown` (`libs/vue/src/lib/combobox/atl-combobox.vue:138-160`) step through all options. Verified: with options A, B (disabled), C, two ArrowDown presses put `aria-activedescendant` on the disabled B in both; Enter on it does nothing. The `A11Y_PARITY_EXEMPT` combobox exemption (`:409`) hides this from the gate. Class c (React, Vue). Fix S, plus a spec. Not breaking.

**6e Accordion.** Metadata: Arrow between headers "within the same group", Home/End.

- Angular: group-owned `handleKeydown` over registered items (`atl-accordion.ts:83-110`). React: `itemsRef` of the group (`atl-accordion.tsx:124-146`); verified, ArrowDown from the last item of group 1 wraps to group 1's first.
- Vue `onKeydown` uses `document.querySelectorAll('.atl-accordion-item:not(.is-disabled) .accordion-trigger')` (`libs/vue/src/lib/accordion/atl-accordion-item.vue:64-85`), ignoring the group. Verified: ArrowDown from the last item of group 1 focuses group 2's first header.
- Also: accordion has no `*.a11y.spec.*` (gate GAP at `allowlists.js:425`), so no cross-framework check.
- Class c (Vue). Fix S: use the group's registered triggers (group already has `registerItem`). Not breaking.

### 7. Items the `check:manifest-parity` list still holds open

- Dialog `aria-labelledby` (Vue): the Vue `AtlDialog` declares no such prop and binds its own `headerId` (`atl-dialog.vue:126-127`), so the manifest shows a gap. Verified: a consumer `aria-labelledby="mine"` on `<AtlDialog>` falls through to the `<dialog>` and wins (probe output `mine`); the dev warning at `:47-61` also reads the attribute. The behaviour is equal in all three, only the declaration differs. Class b. Fix S: JSDoc note or declare the prop; the gap entry can be reclassified. Not breaking.
- Button `type` (Angular): still open. `<atl-button>` is a custom element with `role="button"` and no `type` (`atl-button.ts:25,39-45`); React passes it through `...rest`, Vue has a `type` prop defaulting to `'button'`. The contract says `type` is "not a Figma-drawn visual axis" (settled), so the code gap is separate. Class d: options are an `AtlButton` `type` input that calls `form.requestSubmit()`/`reset()` on click (additive), or changing the selector to `button[atl-button]` (breaking, but native). Effort M.
- Checkbox/Toggle `id` (Angular): still open. `inputId` is fixed to `atl-checkbox-${nextId++}` (`atl-checkbox.ts:96`, `atl-toggle.ts:96`); React and Vue accept `id` (Vue docs: "so an external `<label for>` can point at it"). Class c, fix S (add `id` input defaulting to the generated one), additive. Side note: Vue toggle still builds its id with `Math.random()` inside a `computed` (`atl-toggle.vue:38-40`), unlike checkbox which moved to `useId()`; this risks SSR hydration mismatches.
- Alert `dismissed`: Angular `output` `dismissed`, Vue emit `dismissed`, React `onDismissed` (`atl-alert.tsx:34`). This is framework-idiomatic naming, the same rule as `onPageChange`. It is recorded as `kind: 'gap'`, but it is settled. Class a; reclassify as `design`. Fix S.

## Recommended order

1. Vue a11y/behaviour bugs, all S and non-breaking: tooltip `aria-describedby`, tabs focus, accordion group scoping (6b, 6e, 2).
2. React and Vue combobox disabled-skip (6d), Angular `id` input for checkbox/toggle (7c).
3. Docs-only fixes: stepper JSDoc (3), tooltip React JSDoc and a "no flip" note (2), pagination note (1), select metadata note (6c), dialog and alert reclassification (7a, 7d).
4. Menu keyboard in React and Vue (6a), the only L item and the largest a11y gap; do it with specs per framework.
5. Owner decisions: breadcrumbs `current` (5), `errors` type (4), Angular button `type` (7b).
6. Gate improvements so this does not recur: make `a11y-tree.ts` record `aria-describedby`/`aria-labelledby`, and add a keyboard probe step to the a11y specs (jsdom can check focus movement, which exposed 4 of these).
